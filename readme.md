Полный справочник по паттернам и принципам проектирования
Порождающие паттерны
✅ 1. Builder (Строитель)
Определение:
Строитель — это порождающий паттерн проектирования, который позволяет создавать сложные объекты пошагово.

1. Какую проблему решает:
Проблему "телескопического конструктора" — когда для создания объекта нужно передать множество параметров, большинство из которых опциональны. Это приводит к нечитаемым вызовам new Object(a, null, c, d, null, ...) и ошибкам.

2. Условие применения:

Когда у вас есть конструктор с большим количеством необязательных параметров.

Когда нужно создавать разные конфигурации одного и того же объекта.

Когда код сборки сложного объекта нужно изолировать от его основной бизнес-логики.

3. Каким образом (Решение):
Процесс создания объекта выносится в отдельный класс-Строитель. Вместо прямого вызова конструктора, клиент по шагам вызывает методы строителя, чтобы задать нужные параметры. В конце вызывается метод getResult(), который возвращает готовый объект. Директор (необязательный класс) может инкапсулировать стандартные последовательности сборки.

4. Преимущества и Недостатки:

+ Позволяет создавать объекты по шагам, делая код более читаемым.

+ Изолирует сложный код сборки объекта от его основной бизнес-логики.

+ Позволяет повторно использовать один и тот же код для создания разных представлений объекта.

- Увеличивает сложность кода из-за введения нескольких новых классов и интерфейсов.

Схема и её пояснение:

[Клиент]
    |
    └─ использует -> [ConcreteBuilder] -- создаёт --> [Product]
                      ^
                      | (реализует)
                      |
                   [Builder (интерфейс)]

(Опционально)
[Director] -- управляет --> [Builder]

Клиент напрямую или через Директора работает со Строителем.

Директор знает "рецепты" — последовательности шагов для сборки популярных конфигураций Продукта.

Builder — это интерфейс, который объявляет шаги сборки (например, setSeats, setEngine).

ConcreteBuilder — конкретная реализация строителя. Он выполняет шаги сборки и хранит создаваемый Продукт.

Product — итоговый сложный объект.

Пример на TypeScript:

// Продукт
class HttpRequest {
    public url: string;
    public method: 'GET' | 'POST' = 'GET';
    public headers: Record<string, string> = {};
    public body: any = null;

    constructor(url: string) {
        this.url = url;
    }
    public log(): void { console.log(this); }
}

// Интерфейс Строителя
interface IRequestBuilder {
    setMethod(method: 'GET' | 'POST'): IRequestBuilder;
    setHeaders(headers: Record<string, string>): IRequestBuilder;
    setBody(body: any): IRequestBuilder;
    build(): HttpRequest;
}

// Конкретный строитель
class RequestBuilder implements IRequestBuilder {
    private request: HttpRequest;

    constructor(url: string) {
        this.request = new HttpRequest(url);
    }

    setMethod(method: 'GET' | 'POST'): IRequestBuilder {
        this.request.method = method;
        return this; // Для цепочки вызовов (fluent interface)
    }
    setHeaders(headers: Record<string, string>): IRequestBuilder {
        this.request.headers = headers;
        return this;
    }
    setBody(body: any): IRequestBuilder {
        this.request.body = body;
        return this;
    }
    build(): HttpRequest {
        return this.request;
    }
}

// Клиентский код
const postRequest = new RequestBuilder('https://api.example.com/data')
    .setMethod('POST')
    .setHeaders({ 'Content-Type': 'application/json' })
    .setBody({ id: 1, value: 'test' })
    .build();

postRequest.log();

Объяснение примера:
Вместо конструктора HttpRequest с 4 параметрами мы используем RequestBuilder. Он позволяет пошагово и в любом порядке настраивать запрос, используя понятные методы. Возвращая this, строитель позволяет создавать цепочки вызовов, что делает клиентский код очень читаемым и гибким.

✅ 2. Factory Method (Фабричный метод)
Определение:
Фабричный метод — это порождающий паттерн проектирования, который определяет общий интерфейс для создания объектов в суперклассе, но позволяет подклассам изменять тип создаваемых объектов.

1. Какую проблему решает:
Жесткую привязку кода к конкретным классам создаваемых объектов. Если вы используете new ProductA() напрямую в коде, то для добавления ProductB придется изменять этот код, что нарушает принцип открытости/закрытости.

2. Условие применения:

Когда класс не может заранее знать, объекты каких классов ему нужно создавать.

Когда вы хотите дать возможность пользователям вашей библиотеки или фреймворка расширять его внутренние компоненты.

Когда вы хотите делегировать создание объектов дочерним классам.

3. Каким образом (Решение):
Вместо прямого вызова конструктора (new), клиент вызывает специальный фабричный метод. Этот метод объявлен в базовом классе (Создателе), но его реализация находится в дочерних классах. Каждый дочерний класс-создатель возвращает свой тип продукта, но все продукты имеют общий интерфейс.

4. Преимущества и Недостатки:

+ Ослабляет связь между "клиентом" (кодом, который использует продукт) и "продуктом".

+ Упрощает добавление новых типов продуктов в систему.

- Может привести к созданию большой иерархии классов, параллельной иерархии продуктов.

Схема и её пояснение:

[Клиент]
    |
    v
[Creator (абстрактный)] --------> [Product (интерфейс)]
 |   ^                             ^
 |   | (использует)                | (реализует)
 |   |                             |
 |   └-- factoryMethod() ---┐      |
 |                          |      |
 └---- (реализует) ----> [ConcreteCreator]      [ConcreteProduct]
                            |      ^
                            |      |
                            └-- factoryMethod() --┘

Клиент работает с Создателем через его абстрактный интерфейс.

Creator определяет абстрактный factoryMethod(), который должны реализовать его потомки.

ConcreteCreator реализует factoryMethod и возвращает ConcreteProduct.

Product — это общий интерфейс для всех продуктов, с которым работает Creator.

Пример на TypeScript:

// Интерфейс Продукта
interface ILogger {
    log(message: string): void;
}

// Конкретные Продукты
class ConsoleLogger implements ILogger {
    log(message: string) { console.log(`[CONSOLE]: ${message}`); }
}
class FileLogger implements ILogger {
    log(message: string) { console.log(`Writing to file: ${message}`); }
}

// Абстрактный Создатель
abstract class LoggerFactory {
    // Фабричный метод
    public abstract createLogger(): ILogger;

    public logMessage(message: string): void {
        const logger = this.createLogger();
        logger.log(message);
    }
}

// Конкретные Создатели
class ConsoleLoggerFactory extends LoggerFactory {
    public createLogger(): ILogger {
        return new ConsoleLogger();
    }
}
class FileLoggerFactory extends LoggerFactory {
    public createLogger(): ILogger {
        return new FileLogger();
    }
}

// Клиентский код
function initialize(env: 'development' | 'production'): LoggerFactory {
    if (env === 'production') {
        return new FileLoggerFactory();
    }
    return new ConsoleLoggerFactory();
}

const factory = initialize('development');
factory.logMessage("Application has started.");

Объяснение примера:
Класс LoggerFactory не знает, какой именно логгер создать — консольный или файловый. Он делегирует это решение своим подклассам ConsoleLoggerFactory и FileLoggerFactory через абстрактный createLogger(). Клиентский код определяет, какую фабрику использовать (например, в зависимости от окружения), и работает с ней через общий интерфейс, не привязываясь к конкретным классам логгеров.

✅ 3. Prototype (Прототип)
Определение:
Прототип — это порождающий паттерн проектирования, который позволяет копировать объекты, не вдаваясь в подробности их реализации.

1. Какую проблему решает:
Зависимость кода от классов копируемых объектов. А также создание объекта, которое является дорогостоящим (например, требует запроса к БД или сложных вычислений), но при этом у вас уже есть похожий объект.

2. Условие применения:

Когда создание объекта напрямую (new) слишком затратно.

Когда вы хотите, чтобы ваш код не зависел от конкретных классов создаваемых объектов.

Когда нужно создавать копии объектов со сложным состоянием.

3. Каким образом (Решение):
В класс, объекты которого нужно копировать, добавляется метод clone(). Вместо того чтобы создавать новый объект с нуля, клиент находит существующий объект-прототип и вызывает у него метод clone(). Этот метод создаёт новый объект того же класса и копирует в него значения полей из прототипа.

4. Преимущества и Недостатки:

+ Позволяет клонировать объекты, не привязываясь к их конкретным классам.

+ Ускоряет создание объектов, если их инициализация ресурсоёмка.

- Сложность реализации глубокого копирования для составных объектов (объектов, содержащих ссылки на другие объекты).

Схема и её пояснение:

[Клиент]
    |
    v
[Prototype (интерфейс)] <---- [Registry] (опционально)
    ^                            (хранит прототипы)
    | (реализует)
    |
[ConcretePrototype]
    |
    └-- clone() -- создаёт копию себя --> [New ConcretePrototype]

Клиент запрашивает у Прототипа его копию.

Prototype — это интерфейс с методом clone().

ConcretePrototype — класс, который реализует логику копирования своего состояния.

Registry — необязательный класс, который управляет набором готовых прототипов, доступных по имени.

Пример на TypeScript:

// Продукт с методом клонирования
abstract class Shape {
    constructor(public color: string) {}
    public abstract clone(): Shape;
}

class Circle extends Shape {
    constructor(public radius: number, color: string) {
        super(color);
    }

    public clone(): Shape {
        // Создаем новый объект и копируем состояние
        return new Circle(this.radius, this.color);
    }
}

class Rectangle extends Shape {
     constructor(public width: number, public height: number, color: string) {
        super(color);
    }

    public clone(): Shape {
        return new Rectangle(this.width, this.height, this.color);
    }
}

// Клиентский код
const redCircle = new Circle(10, "red");
const anotherRedCircle = redCircle.clone() as Circle;

console.log(redCircle.radius === anotherRedCircle.radius); // true
console.log(redCircle === anotherRedCircle); // false - это разные объекты

// Проверяем, что изменение копии не влияет на оригинал
anotherRedCircle.color = "blue";
console.log(redCircle.color); // "red"
console.log(anotherRedCircle.color); // "blue"

Объяснение примера:
Классы Circle и Rectangle реализуют метод clone(). Клиенту не нужно знать, как создать круг или прямоугольник с нуля. Он может просто взять существующий объект (например, redCircle) и создать его точную копию. Это особенно полезно, если бы создание фигуры было сложной операцией.

✅ 4. Singleton (Одиночка)
Определение:
Одиночка — это порождающий паттерн проектирования, который гарантирует, что у класса будет только один экземпляр, и предоставляет к нему глобальную точку доступа.

1. Какую проблему решает:
Неконтролируемое создание множества экземпляров объекта, который по своей природе должен быть единственным в системе (например, класс для управления настройками, подключением к БД, логгер). Также решает проблему предоставления удобного глобального доступа к этому экземпляру.

2. Условие применения:

Когда в системе должен существовать ровно один экземпляр класса, доступный всем клиентам.

Когда вам нужен более строгий контроль над глобальными переменными.

3. Каким образом (Решение):

Конструктор класса делается приватным (private), чтобы запретить создание объектов извне через new.

Внутри класса создаётся статическое поле, которое будет хранить единственный экземпляр.

Создаётся публичный статический метод (обычно getInstance()), который возвращает этот экземпляр. При первом вызове он создаёт объект и сохраняет его в статическое поле, а при последующих — просто возвращает уже существующий.

4. Преимущества и Недостатки:

+ Гарантирует наличие одного экземпляра и предоставляет глобальный доступ.

- Нарушает Принцип единственной ответственности (класс контролирует и свою логику, и свой жизненный цикл).

- Маскирует плохой дизайн и создаёт проблемы при многопоточном доступе и тестировании (сложно подменить "моком").

Схема и её пояснение:

[Singleton]
 - instance: Singleton  (статическое поле)
 - constructor()        (приватный)
 + getInstance(): Singleton (статический метод)
      |
      |
      v
[Клиент 1] ----> getInstance()
[Клиент 2] ----> getInstance() ---> (получают тот же самый instance)

Singleton — это класс, который мы хотим ограничить одним экземпляром.

instance — статическое поле, хранящее этот единственный экземпляр.

constructor() — приватный конструктор, недоступный извне.

getInstance() — единственный способ получить объект. Он лениво создаёт его при первом вызове.

Пример на TypeScript:

class AppSettings {
    private static instance: AppSettings;
    public readonly theme: string = 'dark';

    // Конструктор приватный
    private constructor() {
        // Симуляция долгой загрузки настроек
        console.log("Initializing settings...");
    }

    // Статический метод для получения экземпляра
    public static getInstance(): AppSettings {
        if (!AppSettings.instance) {
            AppSettings.instance = new AppSettings();
        }
        return AppSettings.instance;
    }

    public getSettings(): void {
        console.log(`Theme is ${this.theme}`);
    }
}

// Клиентский код
// const settings = new AppSettings(); // Ошибка: конструктор приватный

const s1 = AppSettings.getInstance();
const s2 = AppSettings.getInstance();

if (s1 === s2) {
    console.log('Singleton works, both variables contain the same instance.');
} else {
    console.log('Singleton failed, variables contain different instances.');
}

s1.getSettings();

Объяснение примера:
Класс AppSettings не может быть создан напрямую. Единственный способ получить его объект — вызвать AppSettings.getInstance(). При первом вызове будет выведено "Initializing settings...", а при втором — нет, так как объект уже создан. Переменные s1 и s2 будут ссылаться на один и тот же объект в памяти, что и доказывает работу паттерна.

Структурные паттерны
✅ 5. Adapter (Адаптер)
Определение:
Адаптер — это структурный паттерн проектирования, который позволяет объектам с несовместимыми интерфейсами работать вместе.

1. Какую проблему решает:
Несовместимость между двумя классами, которые должны взаимодействовать. Например, когда вы хотите использовать полезный сторонний класс, но его интерфейс (названия методов, типы данных) не совпадает с тем, который ожидает ваша система.

2. Условие применения:

Когда вы хотите использовать существующий класс, но его интерфейс не соответствует вашим требованиям.

Когда нужно создать единый класс, который бы работал с разными классами с несовместимыми интерфейсами.

3. Каким образом (Решение):
Создаётся класс-Адаптер, который реализует ожидаемый клиентом интерфейс. Внутри себя он "оборачивает" объект с несовместимым интерфейсом (Адаптируемый класс). Когда клиент вызывает метод адаптера, тот, в свою очередь, транслирует этот вызов в вызов метода адаптируемого класса в понятном ему формате.

4. Преимущества и Недостатки:

+ Отделяет и скрывает от клиента детали преобразования интерфейсов.

+ Позволяет использовать сторонние классы, которые невозможно изменить.

- Усложняет код за счёт введения дополнительного класса.

Схема и её пояснение:

[Клиент] ----> [Target (интерфейс)]
                  ^
                  | (реализует)
                  |
               [Adapter]
                  |
                  | (оборачивает и вызывает)
                  v
               [Adaptee (несовместимый класс)]

Клиент работает с целевым интерфейсом Target.

Adaptee — это полезный класс, но с другим интерфейсом.

Adapter реализует интерфейс Target и внутри себя содержит ссылку на Adaptee. Он "переводит" вызовы от клиента к Adaptee.

Пример на TypeScript:

// Целевой интерфейс, который ожидает клиент
interface IDataProcessor {
    processData(data: string): string;
}

// Сторонняя библиотека для аналитики с другим интерфейсом
class XmlAnalyticsLibrary {
    public analyzeXml(xmlData: string): void {
        console.log(`Analyzing XML: ${xmlData}`);
    }
}

// Адаптер: заставляет XmlAnalyticsLibrary работать как IDataProcessor
class XmlToJsonAdapter implements IDataProcessor {
    private adaptee: XmlAnalyticsLibrary;

    constructor(adaptee: XmlAnalyticsLibrary) {
        this.adaptee = adaptee;
    }

    processData(data: string): string {
        console.log("Adapter: Converting JSON to XML...");
        const xml = `<data>${data}</data>`; // симуляция конвертации
        this.adaptee.analyzeXml(xml);
        return "Processed";
    }
}

// Клиентский код
const jsonData = '{"user": "John"}';
const adapter = new XmlToJsonAdapter(new XmlAnalyticsLibrary());
adapter.processData(jsonData);

Объяснение примера:
Нашей системе нужно обрабатывать данные в формате JSON, но у нас есть библиотека, которая работает только с XML (XmlAnalyticsLibrary). XmlToJsonAdapter решает эту проблему: он принимает JSON, внутри конвертирует его в XML и передает в библиотеку. Для клиента это выглядит как обычная обработка данных.

✅ 6. Bridge (Мост)
Определение:
Мост — это структурный паттерн проектирования, который разделяет один или несколько классов на две отдельные иерархии — абстракцию и реализацию, позволяя им изменяться независимо друг от друга.

1. Какую проблему решает:
Проблему "комбинаторного взрыва" классов. Если у вас есть две независимые оси изменчивости (например, фигура и цвет), то без "Моста" вам пришлось бы создавать класс для каждой комбинации (КрасныйКруг, СинийКруг, КрасныйКвадрат и т.д.).

2. Условие применения:

Когда вы хотите разделить большой класс или набор тесно связанных классов на две независимые иерархии.

Когда вы хотите, чтобы и абстракция, и реализация могли изменяться независимо.

Когда нужно иметь возможность переключать реализации в рантайме.

3. Каким образом (Решение):
Создаются две отдельные иерархии. Первая — Абстракция (например, Shape), которая содержит основную, высокоуровневую логику и хранит ссылку на объект из второй иерархии. Вторая — Реализация (например, Color), которая содержит низкоуровневую, платформо-зависимую логику. Абстракция делегирует выполнение низкоуровневых операций объекту-реализации.

4. Преимущества и Недостатки:

+ Позволяет независимо изменять абстракции и реализации.

+ Уменьшает количество классов, соответствует Принципу открытости/закрытости.

- Усложняет код из-за введения дополнительных классов и интерфейсов.

Схема и её пояснение:

[Клиент] --> [Абстракция] <>---- [Реализация (интерфейс)]
               ^                     ^
               | (наследует)         | (реализует)
               |                     |
            [Уточн. абстракция]   [Конкр. реализация A]
                                  [Конкр. реализация B]

Абстракция определяет высокоуровневый интерфейс и хранит ссылку на объект Реализации.

Уточненная абстракция расширяет Абстракцию.

Реализация определяет интерфейс для низкоуровневых операций.

Конкретные реализации реализуют этот интерфейс.

Пример на TypeScript:

// Интерфейс Реализации (Устройство)
interface IDevice {
    turnOn(): void;
    turnOff(): void;
    setChannel(channel: number): void;
}

// Конкретные Реализации
class Tv implements IDevice {
    turnOn() { console.log("TV is ON"); }
    turnOff() { console.log("TV is OFF"); }
    setChannel(channel: number) { console.log(`TV channel set to ${channel}`); }
}
class Radio implements IDevice {
    turnOn() { console.log("Radio is ON"); }
    turnOff() { console.log("Radio is OFF"); }
    setChannel(channel: number) { console.log(`Radio station set to ${channel} FM`); }
}

// Абстракция (Пульт)
class RemoteControl {
    protected device: IDevice; // Мост!

    constructor(device: IDevice) {
        this.device = device;
    }

    togglePower() {
        this.device.turnOn(); // Предположим, для простоты
    }
}

// Уточненная Абстракция
class AdvancedRemoteControl extends RemoteControl {
    mute() {
        console.log("Device muted");
    }
}

// Клиентский код
const tv = new Tv();
const remoteForTv = new RemoteControl(tv);
remoteForTv.togglePower();

const radio = new Radio();
const advancedRemoteForRadio = new AdvancedRemoteControl(radio);
advancedRemoteForRadio.togglePower();
advancedRemoteForRadio.mute();

Объяснение примера:
Мы разделили иерархии Пультов (RemoteControl) и Устройств (Device). Теперь мы можем создавать новые типы пультов (например, с кнопкой mute) и новые типы устройств, и они будут работать вместе без необходимости создавать класс для каждой пары (например, TVRemote, RadioRemote). Пульт содержит ссылку на устройство — это и есть "мост".

✅ 7. Composite (Компоновщик)
Определение:
Компоновщик — это структурный паттерн проектирования, который позволяет сгруппировать множество объектов в древовидную структуру, а затем работать с этой структурой так, как будто это единичный объект.

1. Какую проблему решает:
Необходимость писать разный код для работы с простыми элементами ("листьями") и их контейнерами ("узлами"). Например, при расчёте стоимости заказа нужно по-разному обрабатывать отдельный товар и целую коробку с товарами.

2. Условие применения:

Когда ваша модель может быть представлена в виде дерева (графические примитивы, структура меню, дерево папок, организационная структура).

Когда вы хотите, чтобы клиенты единообразно трактовали как простые, так и составные объекты.

3. Каким образом (Решение):
Создаётся общий интерфейс Компонента, который реализуют как простые Листья, так и составные Контейнеры. Контейнер хранит внутри себя список дочерних компонентов (которые могут быть как листьями, так и другими контейнерами). Когда клиент вызывает операцию у контейнера, тот делегирует её выполнение своим дочерним элементам.

4. Преимущества и Недостатки:

+ Упрощает архитектуру клиента, позволяя ему единообразно работать с деревом.

+ Позволяет легко добавлять новые виды элементов в структуру.

- Может быть сложно создать общую логику для слишком разных классов.

Схема и её пояснение:

[Клиент] ---> [Component (интерфейс)]
                  ^
      ____________|____________
     |                         |
  (реализует)               (реализует)
     |                         |
   [Leaf]                  [Composite]
                               |
                               | (содержит список)
                               v
                            [Component]

Component определяет общий интерфейс для всех объектов в структуре.

Leaf — простой, неделимый элемент дерева.

Composite — узел, который может иметь дочерние элементы (Component).

Пример на TypeScript:

// Общий интерфейс Компонента
interface IPriceable {
    getPrice(): number;
}

// Лист (Продукт)
class Product implements IPriceable {
    constructor(public name: string, public price: number) {}
    getPrice(): number { return this.price; }
}

// Контейнер (Коробка)
class Box implements IPriceable {
    private children: IPriceable[] = [];

    add(component: IPriceable): void {
        this.children.push(component);
    }

    getPrice(): number {
        // Рекурсивно вычисляет стоимость
        return this.children.reduce((total, child) => total + child.getPrice(), 0);
    }
}

// Клиентский код
const mainBox = new Box();
const phone = new Product("iPhone", 1000);
const headphones = new Product("AirPods", 200);

const accessoriesBox = new Box();
const charger = new Product("Charger", 50);
const caseItem = new Product("Case", 30);

accessoriesBox.add(charger);
accessoriesBox.add(caseItem);

mainBox.add(phone);
mainBox.add(headphones);
mainBox.add(accessoriesBox);

console.log(`Total order price: $${mainBox.getPrice()}`); // $1280

Объяснение примера:
И Product, и Box реализуют общий интерфейс IPriceable. Это позволяет клиенту вызывать getPrice() у любого элемента, не задумываясь, товар это или целая коробка. Если это коробка, она сама позаботится о том, чтобы опросить все свои дочерние элементы и сложить их стоимость.

✅ 8. Decorator (Декоратор)
Определение:
Декоратор — это структурный паттерн проектирования, который позволяет динамически добавлять объектам новую функциональность, оборачивая их в полезные «обёртки».

1. Какую проблему решает:
Необходимость расширять функциональность объекта без использования наследования, которое является статичным и менее гибким. Если использовать наследование для всех комбинаций фич (например, Уведомление -> Email -> SMS -> Slack), это приведёт к "взрыву" количества классов.

2. Условие применения:

Когда нужно добавлять/убирать обязанности у объекта "на лету", динамически.

Когда расширение класса с помощью наследования неудобно или невозможно.

3. Каким образом (Решение):
Создаётся базовый интерфейс Компонента. Затем создаётся абстрактный класс Декоратор, который тоже реализует этот интерфейс и содержит ссылку на оборачиваемый компонент. Конкретные декораторы наследуются от него и добавляют свою логику до или после вызова метода у оборачиваемого объекта. Декораторы можно вкладывать друг в друга как матрёшку.

4. Преимущества и Недостатки:

+ Большая гибкость, чем у наследования; можно добавлять/убирать обязанности в рантайме.

+ Не ломает принцип единственной ответственности.

- Может привести к созданию множества мелких классов-обёрток.

- Сложно убрать конкретную обёртку из середины "стопки".

Схема и её пояснение:

[Клиент] -> [Component (интерфейс)]
               ^
   ____________|____________
  |                         |
(реализует)               (реализует)
  |                         |
[ConcreteComponent]       [Decorator] <>-- [Component]
                             ^
                 ____________|____________
                |                         |
             (наследует)               (наследует)
                |                         |
             [ConcreteDecoratorA]      [ConcreteDecoratorB]

Component - общий интерфейс для оборачиваемых объектов и декораторов.

ConcreteComponent - базовый объект, которому мы добавляем поведение.

Decorator - базовый класс для всех декораторов, хранит ссылку на оборачиваемый объект.

ConcreteDecorator - добавляет новую функциональность.

Пример на TypeScript:

// Общий интерфейс
interface INotifier {
    send(message: string): void;
}

// Базовый компонент
class EmailNotifier implements INotifier {
    send(message: string): void {
        console.log(`Sending email with message: ${message}`);
    }
}

// Базовый Декоратор
abstract class NotifierDecorator implements INotifier {
    protected wrappee: INotifier;

    constructor(notifier: INotifier) {
        this.wrappee = notifier;
    }

    send(message: string): void {
        this.wrappee.send(message);
    }
}

// Конкретные декораторы
class SMSDecorator extends NotifierDecorator {
    send(message: string): void {
        super.send(message); // Сначала отправляем email
        console.log(`Sending SMS with message: ${message}`);
    }
}
class SlackDecorator extends NotifierDecorator {
    send(message: string): void {
        super.send(message);
        console.log(`Sending Slack message: ${message}`);
    }
}

// Клиентский код
let notifier: INotifier = new EmailNotifier();
notifier = new SMSDecorator(notifier);
notifier = new SlackDecorator(notifier);

notifier.send("The build has failed!");

Объяснение примера:

У нас есть базовый EmailNotifier.

Мы "оборачиваем" его в SMSDecorator, чтобы добавить отправку SMS.

Затем мы оборачиваем результат в SlackDecorator, чтобы добавить уведомления в Slack.

Когда мы вызываем send(), вызов проходит по всей цепочке: Slack -> SMS -> Email. Таким образом, мы динамически собрали нужную нам функциональность.

✅ 9. Facade (Фасад)
Определение:
Фасад — это структурный паттерн проектирования, который предоставляет простой, единый интерфейс к сложной подсистеме, состоящей из множества классов.

1. Какую проблему решает:
Сложность работы со сложной подсистемой или фреймворком. Клиентскому коду приходится вникать во множество деталей и управлять жизненным циклом разных объектов подсистемы, что создаёт сильную связанность.

2. Условие применения:

Когда нужно предоставить простой и ограниченный доступ к сложной подсистеме.

Когда нужно разложить подсистему на слои и уменьшить количество зависимостей между клиентом и подсистемой.

3. Каким образом (Решение):
Создаётся класс-Фасад, который инкапсулирует всю сложность взаимодействия с компонентами подсистемы. Он предоставляет клиенту несколько простых высокоуровневых методов, а внутри себя уже вызывает нужные методы у нужных объектов подсистемы в правильном порядке.

4. Преимущества и Недостатки:

+ Изолирует клиентов от сложности подсистемы.

+ Ослабляет связанность между клиентом и компонентами подсистемы.

- Фасад может стать "божественным объектом", привязанным ко всем классам подсистемы.

Схема и её пояснение:

[Клиент] ----> [Фасад]
                  |
    ┌-------------+-------------┐
    |             |             |
    v             v             v
[Класс_А]     [Класс_Б]     [Класс_В]
\___________________________________/
         Сложная подсистема

Клиент взаимодействует только с Фасадом.

Фасад знает, как работать со сложной подсистемой (Класс_А, Класс_Б, Класс_В), и скрывает эту сложность.

Пример на TypeScript:

// Части сложной подсистемы
class VideoConverter { convert(file: string, format: string): string { return 'converted_video'; } }
class AudioExtractor { extract(file: string): string { return 'extracted_audio'; } }
class Uploader { upload(file: string, destination: string): void { console.log(`Uploading ${file} to ${destination}`); } }

// Фасад
class VideoProcessingFacade {
    private converter = new VideoConverter();
    private extractor = new AudioExtractor();
    private uploader = new Uploader();

    public processAndUpload(file: string): void {
        console.log("Facade: Starting video processing...");
        const video = this.converter.convert(file, 'mp4');
        const audio = this.extractor.extract(video);
        this.uploader.upload(video, 'youtube.com');
        this.uploader.upload(audio, 'spotify.com');
        console.log("Facade: Processing finished.");
    }
}

// Клиентский код
const facade = new VideoProcessingFacade();
facade.processAndUpload("my_vacation.mov");

Объяснение примера:
Клиенту не нужно знать о существовании классов VideoConverter, AudioExtractor и Uploader. Он просто вызывает один метод processAndUpload у VideoProcessingFacade, который оркестрирует всю сложную работу под капотом.

✅ 10. Flyweight (Приспособленец)
Определение:
Приспособленец — это структурный паттерн проектирования, который позволяет вместить большее количество объектов в отведённую оперативную память за счёт разделения общего состояния объектов между собой.

1. Какую проблему решает:
Высокое потребление памяти из-за создания огромного количества однотипных объектов, которые содержат много дублирующихся данных (например, отрисовка миллионов деревьев в игре).

2. Условие применения:

Когда программа должна поддерживать огромное количество объектов, и они не помещаются в память.

Когда большую часть состояния объекта можно вынести за его пределы и сделать общей.

3. Каким образом (Решение):
Состояние объекта разделяется на две части: внутреннее (общее, неизменяемое, например, текстура и модель дерева) и внешнее (уникальное для каждого экземпляра, например, координаты и размер дерева). Внутреннее состояние хранится в объекте-Приспособленце. Уникальное внешнее состояние передаётся в методы приспособленца извне. Для управления приспособленцами используется Фабрика приспособленцев.

4. Преимущества и Недостатки:

+ Значительно экономит оперативную память.

- Усложняет код из-за необходимости разделять состояния и передавать внешнее состояние в методы.

- Может немного снизить производительность из-за дополнительных вычислений внешнего состояния.

Схема и её пояснение:

[Клиент] ---> [FlyweightFactory] ---> [Flyweight]
                     ^                   ^ |
                     | (создаёт/выдаёт)    | | (имеет внутреннее состояние)
                     |                   | v
                     └-------------------┘ [Контекст] (имеет внешнее состояние)

Flyweight хранит общее (внутреннее) состояние.

FlyweightFactory создаёт и кеширует приспособленцев.

Контекст хранит уникальное (внешнее) состояние и ссылку на приспособленца.

Клиент работает с фабрикой и контекстами.

Пример на TypeScript:

// Приспособленец (внутреннее состояние)
class TreeType {
    constructor(public name: string, public color: string, public texture: string) {}

    draw(canvas: any, x: number, y: number) {
        console.log(`Drawing a ${this.name} tree at (${x}, ${y}) with color ${this.color}`);
    }
}

// Фабрика Приспособленцев
class TreeFactory {
    private static treeTypes: Map<string, TreeType> = new Map();

    public static getTreeType(name: string, color: string, texture: string): TreeType {
        const key = `${name}_${color}`;
        if (!this.treeTypes.has(key)) {
            console.log(`Factory: Creating a new tree type: ${key}`);
            this.treeTypes.set(key, new TreeType(name, color, texture));
        }
        return this.treeTypes.get(key)!;
    }
}

// Контекст (внешнее состояние)
class Tree {
    constructor(private x: number, private y: number, private type: TreeType) {}

    draw(canvas: any) {
        this.type.draw(canvas, this.x, this.y);
    }
}

// Клиентский код
const forest: Tree[] = [];
forest.push(new Tree(10, 20, TreeFactory.getTreeType("Oak", "Green", "oak.png")));
forest.push(new Tree(50, 60, TreeFactory.getTreeType("Oak", "Green", "oak.png")));
forest.push(new Tree(90, 30, TreeFactory.getTreeType("Birch", "White", "birch.png")));

forest.forEach(tree => tree.draw(null));

Объяснение примера:
Вместо создания тысяч объектов Tree с полями name, color, texture, мы создаем всего два объекта TreeType (дуб и берёза), которые хранят эти общие данные. Объекты Tree содержат только уникальные координаты x, y и ссылку на соответствующий TreeType. Это радикально снижает потребление памяти.

✅ 11. Proxy (Заместитель)
Определение:
Заместитель — это структурный паттерн проектирования, который позволяет подставлять вместо реальных объектов специальные объекты-заменители. Эти объекты перехватывают вызовы к оригинальному объекту, позволяя сделать что-то до или после передачи вызова оригиналу.

1. Какую проблему решает:
Необходимость добавить дополнительную логику к существующему классу без его изменения. Позволяет управлять доступом к объекту, его созданием или поведением.

2. Условие применения:

Ленивая инициализация (виртуальный прокси): когда у вас есть тяжёлый объект, создание которого нужно отложить.

Контроль доступа (защищающий прокси): когда нужно проверять права клиента перед выполнением запроса.

Логирование/Кеширование (умный прокси): когда нужно выполнить дополнительные действия до или после обращения к объекту.

3. Каким образом (Решение):
Создаётся объект-Заместитель, который имеет тот же интерфейс, что и Реальный объект. Клиент работает с заместителем, как с оригиналом. Прокси содержит ссылку на реальный объект и решает, когда и как передать ему вызов. Например, он может создать реальный объект только при первом вызове метода.

4. Преимущества и Недостатки:

+ Позволяет управлять жизненным циклом и доступом к сервисному объекту незаметно для клиента.

+ Работает, даже если сервисный объект недоступен или его создание дорого.

- Усложняет код дополнительным классом.

- Ответ от сервиса может приходить с задержкой (например, при ленивой инициализации).

Схема и её пояснение:

[Клиент] ----> [Subject (интерфейс)]
                  ^
      ____________|____________
     |                         |
  (реализует)               (реализует)
     |                         |
 [RealSubject] <---------- [Proxy]
                             |
                             | (может содержать ссылку)
                             v
                          [RealSubject]

Subject — общий интерфейс для реального объекта и прокси.

RealSubject — "тяжёлый" или защищённый объект.

Proxy реализует тот же интерфейс и контролирует доступ к RealSubject.

Пример на TypeScript:

// Общий интерфейс
interface IImage {
    display(): void;
}

// Реальный объект
class RealImage implements IImage {
    private fileName: string;
    constructor(fileName: string) {
        this.fileName = fileName;
        this.loadFromDisk();
    }
    private loadFromDisk(): void {
        console.log(`Loading image: ${this.fileName}`);
    }
    display(): void {
        console.log(`Displaying image: ${this.fileName}`);
    }
}

// Прокси (ленивая загрузка)
class ProxyImage implements IImage {
    private realImage: RealImage | null = null;
    private fileName: string;

    constructor(fileName: string) {
        this.fileName = fileName;
    }

    display(): void {
        if (this.realImage === null) {
            console.log("Proxy: creating real image object now.");
            this.realImage = new RealImage(this.fileName);
        }
        this.realImage.display();
    }
}

// Клиентский код
const image = new ProxyImage("photo.jpg");
console.log("Image object created, but not loaded yet.");

// Изображение загрузится только сейчас, при первом вызове display()
image.display(); 

console.log("\nSecond call to display():");
image.display(); // Загрузка не произойдет снова

Объяснение примера:
Создание объекта RealImage — дорогая операция, так как он сразу загружает файл с диска. ProxyImage откладывает создание RealImage до тех пор, пока не будет вызван метод display(). Это экономит ресурсы, если изображение так и не понадобится отображать.

Поведенческие паттерны
✅ 12. Chain of Responsibility (Цепочка обязанностей)
Определение:
Цепочка обязанностей — это поведенческий паттерн проектирования, который позволяет передавать запросы последовательно по цепочке обработчиков. Каждый обработчик решает, может ли он обработать запрос сам, или его нужно передать дальше по цепочке.

1. Какую проблему решает:
Жесткую привязку отправителя запроса к его получателю. В обычной ситуации отправитель должен знать, какому именно объекту адресован запрос. Паттерн позволяет нескольким объектам поочередно получить шанс обработать запрос.

2. Условие применения:

Когда запрос может быть обработан разными объектами, и точный обработчик заранее неизвестен.

Когда важно, чтобы обработчики шли в строгом порядке.

Когда набор обработчиков и их порядок могут меняться динамически.

3. Каким образом (Решение):
Объекты-Обработчики выстраиваются в Цепочку. Каждый обработчик содержит ссылку на следующий в цепочке. Получив запрос, обработчик либо выполняет его, либо передаёт следующему. Клиент отправляет запрос только первому обработчи-ку в цепочке.

4. Преимущества и Недостатки:

+ Ослабляет связь между клиентом и обработчиками.

+ Гибкая настройка порядка обработчиков.

+ Соответствует Принципу единственной ответственности.

- Запрос может остаться никем не обработанным, если цепочка настроена неверно.

Схема и её пояснение:

[Клиент] -> [Обработчик A] -> [Обработчик B] -> [Обработчик C] -> null

Клиент отправляет запрос первому обработчику.

Каждый Обработчик имеет ссылку на следующего. Он анализирует запрос: если может обработать — обрабатывает, если нет — передаёт дальше по цепочке.

Пример на TypeScript:

// Интерфейс обработчика
interface IHandler {
    setNext(handler: IHandler): IHandler;
    handle(request: string): string | null;
}

abstract class AbstractHandler implements IHandler {
    private nextHandler: IHandler | null = null;

    public setNext(handler: IHandler): IHandler {
        this.nextHandler = handler;
        return handler;
    }

    public handle(request: string): string | null {
        if (this.nextHandler) {
            return this.nextHandler.handle(request);
        }
        return null;
    }
}

class AdminAuthHandler extends AbstractHandler {
    public handle(request: string): string | null {
        if (request === 'admin_password') {
            return `AdminAuthHandler: Welcome, admin!`;
        }
        return super.handle(request);
    }
}
class UserAuthHandler extends AbstractHandler {
    public handle(request: string): string | null {
        if (request === 'user_password') {
            return `UserAuthHandler: Welcome, user!`;
        }
        return super.handle(request);
    }
}

// Клиентский код
const adminHandler = new AdminAuthHandler();
const userHandler = new UserAuthHandler();

adminHandler.setNext(userHandler); // Строим цепочку: admin -> user

console.log(`Client: Trying 'user_password'`);
console.log(adminHandler.handle('user_password'));

console.log(`\nClient: Trying 'admin_password'`);
console.log(adminHandler.handle('admin_password'));

console.log(`\nClient: Trying 'wrong_password'`);
console.log(adminHandler.handle('wrong_password'));

Объяснение примера:
Мы создали цепочку обработчиков аутентификации. Сначала запрос попадает в AdminAuthHandler. Если пароль не подходит для админа, он передаёт запрос дальше по цепочке — в UserAuthHandler. Если и тот не может обработать запрос, возвращается null.

✅ 13. Command (Команда)
Определение:
Команда — это поведенческий паттерн проектирования, который превращает запрос в самостоятельный объект, содержащий всю информацию об этом запросе. Это позволяет параметризовать методы с разными запросами, ставить запросы в очередь, логировать их, а также поддерживать отмену операций.

1. Какую проблему решает:
Сильную зависимость между объектом, который инициирует операцию (отправителем), и объектом, который её выполняет (получателем). Паттерн позволяет инкапсулировать запрос как объект.

2. Условие применения:

Когда нужно параметризовать объекты выполняемым действием.

Когда нужно ставить операции в очередь, выполнять их по расписанию.

Когда нужна поддержка отмены/повтора операций.

3. Каким образом (Решение):
Вместо прямого вызова метода у получателя, Отправитель создаёт объект-Команду. Этот объект содержит ссылку на Получателя и всю информацию, необходимую для выполнения действия. У всех команд есть общий метод execute(). Отправитель просто вызывает этот метод, не зная, что именно будет выполнено.

4. Преимущества и Недостатки:

+ Убирает прямую связь между объектами.

+ Позволяет реализовать отмену/повтор операций.

+ Позволяет собирать сложные команды из простых.

- Усложняет код, добавляя много новых классов.

Схема и её пояснение:

[Отправитель] ---> [Команда (интерфейс)] <--- [Конкретная Команда]
    |                      (execute)                        |
    |                                                       | (содержит ссылку)
    v                                                       v
(вызывает execute)                                      [Получатель]
                                                            |
                                                            v
                                                        (выполняет действие)

Отправитель (Invoker) хранит и инициирует команду.

Команда (Command) — интерфейс с методом execute().

Конкретная Команда (ConcreteCommand) реализует execute, вызывая нужный метод у Получателя.

Получатель (Receiver) — объект, который выполняет основную работу.

Пример на TypeScript:

// Получатель
class TextEditor {
    public content: string = "";
    public copy() { console.log("Text copied"); }
    public paste() { console.log("Text pasted"); }
}

// Интерфейс Команды
interface ICommand {
    execute(): void;
}

// Конкретные Команды
class CopyCommand implements ICommand {
    constructor(private editor: TextEditor) {}
    execute(): void { this.editor.copy(); }
}
class PasteCommand implements ICommand {
    constructor(private editor: TextEditor) {}
    execute(): void { this.editor.paste(); }
}

// Отправитель
class Button {
    private command!: ICommand;
    setCommand(command: ICommand) { this.command = command; }
    click(): void { this.command.execute(); }
}

// Клиентский код
const editor = new TextEditor();
const copyButton = new Button();
copyButton.setCommand(new CopyCommand(editor));
copyButton.click();

const pasteButton = new Button();
pasteButton.setCommand(new PasteCommand(editor));
pasteButton.click();

Объяснение примера:
Класс Button не знает ничего о текстовом редакторе. Он просто знает, что у него есть command, у которой можно вызвать execute(). Мы можем "настроить" кнопку на выполнение любой команды (копирование, вставка, вырезание), не меняя код самой кнопки.

✅ 14. Interpreter (Интерпретатор)
Определение:
Интерпретатор — это поведенческий паттерн проектирования, который решает часто встречающуюся, но изменчивую задачу, предоставляя для неё собственный язык и механизм его разбора.

1. Какую проблему решает:
Наличие множества похожих, но не идентичных задач, которые можно описать единым языком (например, поиск по разным критериям, правила валидации). Реализация этого через условные операторы приводит к сложному и негибкому коду.

2. Условие применения:

Когда есть простой язык, и вы можете представить его выражения в виде синтаксического дерева (AST).

Когда эффективность не является критическим фактором (интерпретация обычно медленнее компиляции).

(Примечание: этот паттерн используется довольно редко в повседневной разработке).

3. Каким образом (Решение):
Для каждой грамматической конструкции языка (терминального и нетерминального выражения) создаётся свой класс. Эти классы реализуют общий интерфейс Expression. Выражения можно комбинировать друг с другом, строя синтаксическое дерево. Вызов метода interpret() у корневого узла запускает рекурсивный обход всего дерева.

4. Преимущества и Недостатки:

+ Гибкость и лёгкость расширения грамматики (достаточно добавить новый класс выражения).

+ Логика каждого выражения инкапсулирована в своём классе.

- Сложность реализации для языков со сложной грамматикой.

- Низкая производительность.

Схема и её пояснение:

[Клиент]
    |
    v
[Контекст] (содержит глобальную информацию)
    |
    |
    v
[Выражение (интерфейс)] <---- [Терминальное выражение]
    ^                          (конечный узел)
    |
    |
    └--- [Нетерминальное выражение]
              |
              | (содержит другие выражения)
              v
           [Выражение]

Клиент создает синтаксическое дерево из выражений.

Контекст передается в интерпретатор и содержит данные для разбора.

Выражение — общий интерфейс с методом interpret().

Терминальное выражение представляет "лист" дерева.

Нетерминальное выражение представляет узел, состоящий из других выражений.

Пример на TypeScript:

// Контекст
const context = { A: true, B: false, C: true };

// Интерфейс
interface IExpression { interpret(context: any): boolean; }

// Терминальное выражение
class Variable implements IExpression {
    constructor(private name: string) {}
    interpret(context: any): boolean { return context[this.name]; }
}

// Нетерминальные выражения
class And implements IExpression {
    constructor(private left: IExpression, private right: IExpression) {}
    interpret(context: any): boolean {
        return this.left.interpret(context) && this.right.interpret(context);
    }
}
class Or implements IExpression {
    constructor(private left: IExpression, private right: IExpression) {}
    interpret(context: any): boolean {
        return this.left.interpret(context) || this.right.interpret(context);
    }
}

// Клиентский код: строим дерево для выражения "A and (B or C)"
const a = new Variable("A");
const b = new Variable("B");
const c = new Variable("C");

const expression = new And(a, new Or(b, c));
console.log(expression.interpret(context)); // true && (false || true) -> true

Объяснение примера:
Мы создали простой язык для логических выражений. Вместо написания if (context.A && (context.B || context.C)), мы строим объектное дерево, которое представляет это выражение. Это позволяет нам легко создавать, изменять и разбирать сложные правила динамически.

✅ 15. Iterator (Итератор)
Определение:
Итератор — это поведенческий паттерн проектирования, который даёт возможность последовательно обходить элементы составных объектов, не раскрывая их внутреннего представления.

1. Какую проблему решает:
Раскрытие внутренней структуры коллекции (например, массива, списка, дерева). Если клиентский код напрямую работает с внутренностями коллекции, то любое изменение в ней (например, замена массива на хэш-таблицу) ломает клиентский код.

2. Условие применения:

Когда нужно скрыть детали реализации сложной структуры данных от клиента, но предоставить ему способ обхода её элементов.

Когда нужно поддерживать несколько различных способов обхода одной и той же коллекции.

Когда нужен единый интерфейс для обхода разных структур данных.

3. Каким образом (Решение):
Логика обхода выносится из коллекции в отдельный класс-Итератор. Коллекция предоставляет метод для получения итератора. У итератора есть стандартные методы (например, hasNext() и next()), через которые клиент и осуществляет обход, не зная, как коллекция устроена внутри.

4. Преимущества и Недостатки:

+ Скрывает внутреннее устройство коллекции.

+ Позволяет реализовать разные способы обхода (например, в прямом и обратном порядке).

+ Упрощает код клиента и коллекции.
-` Может быть избыточным для простых коллекций.

Схема и её пояснение:

[Клиент] ---> [Коллекция (интерфейс)] ---> [Итератор (интерфейс)]
                 ^                               ^
                 | (реализует)                   | (реализует)
                 |                               |
               [Конкретная Коллекция]   [Конкретный Итератор]
                 |                               ^
                 |                               |
                 └----- createIterator() ---------┘

Клиент просит у Коллекции создать Итератор.

Коллекция создает Конкретный итератор, передавая ему ссылку на себя или свои данные.

Клиент использует методы итератора (next, hasNext) для обхода.

Пример на TypeScript:

interface IIterator<T> {
    next(): T;
    hasNext(): boolean;
}

class ArrayIterator<T> implements IIterator<T> {
    private position = 0;
    constructor(private collection: T[]) {}

    public next(): T {
        const result = this.collection[this.position];
        this.position++;
        return result;
    }

    public hasNext(): boolean {
        return this.position < this.collection.length;
    }
}

class WordsCollection {
    private items: string[] = [];
    public getItems(): string[] { return this.items; }
    public addItem(item: string): void { this.items.push(item); }
    public createIterator(): IIterator<string> {
        return new ArrayIterator(this.items);
    }
}

// Клиентский код
const collection = new WordsCollection();
collection.addItem("First");
collection.addItem("Second");
collection.addItem("Third");

const iterator = collection.createIterator();
while (iterator.hasNext()) {
    console.log(iterator.next());
}

Объяснение примера:
Клиентский код не знает, что WordsCollection внутри использует массив string[]. Он просто получает итератор и использует его стандартные методы. Если мы заменим внутренний массив на другую структуру, нам нужно будет поменять только WordsCollection, а клиентский код останется без изменений.

✅ 16. Mediator (Посредник)
Определение:
Посредник — это поведенческий паттерн проектирования, который позволяет уменьшить связанность множества классов между собой, заставляя их взаимодействовать не напрямую, а через единый объект-посредник.

1. Какую проблему решает:
Проблему "спагетти-кода", когда множество компонентов (например, элементы GUI) тесно связаны друг с другом и напрямую вызывают методы друг друга. Это делает систему сложной для понимания, поддержки и переиспользования отдельных компонентов.

2. Условие применения:

Когда у вас есть набор объектов, связи между которыми сложны и запутаны.

Когда вы хотите переиспользовать компонент, но он сильно зависит от других компонентов.

3. Каким образом (Решение):
Создаётся центральный объект-Посредник, который инкапсулирует все связи между Компонентами. Компоненты больше не знают друг о друге, они знают только о посреднике. Когда в компоненте происходит событие, он уведомляет посредника, а тот уже решает, какие другие компоненты должны на это отреагировать.

4. Преимущества и Недостатки:

+ Убирает прямые связи между компонентами, уменьшая их зацепление.

+ Упрощает взаимодействие между компонентами.

+ Централизует управление взаимодействием.

- Посредник может превратиться в "божественный объект", который сложно поддерживать.

Схема и её пояснение:

[Компонент A] <---> [Посредник] <---> [Компонент B]
     ^                                  ^
     |                                  |
     └----------------------------------┘
               (общаются только через Посредника)

Компоненты (A, B) — независимые классы, которые раньше были связаны напрямую.

Посредник — центральный объект, который получает уведомления от компонентов и перенаправляет их другим компонентам.

Пример на TypeScript:

// Интерфейс Посредника
interface IMediator {
    notify(sender: object, event: string): void;
}

// Конкретные компоненты
class Checkbox {
    constructor(private dialog: IMediator) {}
    public check(): void {
        console.log("Checkbox checked!");
        this.dialog.notify(this, 'checkboxChecked');
    }
}
class SubmitButton {
    public isEnabled: boolean = false;
    constructor(private dialog: IMediator) {}
    public click(): void {
        if(this.isEnabled) {
             console.log("Submit button clicked!");
             this.dialog.notify(this, 'submit');
        } else {
             console.log("Submit button is disabled.");
        }
    }
}

// Конкретный Посредник
class AuthDialog implements IMediator {
    private checkbox: Checkbox;
    private submitButton: SubmitButton;

    constructor() {
        this.checkbox = new Checkbox(this);
        this.submitButton = new SubmitButton(this);
    }

    public notify(sender: object, event: string): void {
        if (event === 'checkboxChecked') {
            console.log('Mediator: Checkbox was checked. Enabling submit button.');
            this.submitButton.isEnabled = true;
        }
        if (event === 'submit') {
            console.log('Mediator: Submit button was clicked. Processing...');
        }
    }

    // Методы для симуляции взаимодействия
    public simulateUserAction(): void {
        this.submitButton.click(); // disabled
        this.checkbox.check();
        this.submitButton.click(); // enabled
    }
}

// Клиентский код
const dialog = new AuthDialog();
dialog.simulateUserAction();

Объяснение примера:
В диалоговом окне AuthDialog есть чекбокс и кнопка "Отправить". Кнопка должна быть активна только когда чекбокс отмечен. Вместо того чтобы чекбокс напрямую вызывал метод у кнопки, он уведомляет диалог (AuthDialog), который выступает в роли Посредника. Посредник, получив уведомление, активирует кнопку. Таким образом, чекбокс и кнопка не знают о существовании друг друга.

✅ 17. Memento (Снимок)
Определение:
Снимок — это поведенческий паттерн проектирования, который позволяет сохранять и восстанавливать прошлое состояние объекта, не раскрывая деталей его реализации.

1. Какую проблему решает:
Необходимость реализовать механизм отмены/возврата (Undo) или создавать "точки сохранения", не нарушая при этом инкапсуляцию. Делать все поля объекта публичными для сохранения — плохая практика.

2. Условие применения:

Когда нужно делать "снимки" состояния объекта для последующего восстановления.

Когда прямой доступ к полям объекта нарушает его инкапсуляцию.

3. Каким образом (Решение):
Паттерн вводит три роли: Хозяин (Originator) — объект, состояние которого мы сохраняем; Снимок (Memento) — объект, который хранит состояние Хозяина; и Опекун (Caretaker) — объект, который хранит снимки, но не имеет доступа к их содержимому. Хозяин создаёт снимок со своим состоянием и отдаёт его Опекуну. Позже Опекун может вернуть снимок Хозяину для восстановления состояния.

4. Преимущества и Недостатки:

+ Не нарушает инкапсуляцию исходного объекта.

+ Упрощает структуру Хозяина, вынося из него логику хранения истории.

- Может требовать много памяти, если состояния объектов велики и история длинная.

Схема и её пояснение:

[Опекун] <>---- [Снимок] <---- [Хозяин]
   |             ^   |             |
   | (хранит)    |   | (создаёт)   |
   |             |   |             | (восстанавливает состояние из)
   └-------------┘   └-------------┘

Хозяин создаёт Снимок и может восстановить своё состояние из него.

Снимок — это простой объект, хранящий данные. Его внутренности доступны только Хозяину.

Опекун хранит стопку Снимков, но не может изменять или читать их.

Пример на TypeScript:

// Снимок
class EditorMemento {
    constructor(public readonly content: string) {}
}

// Хозяин
class TextEditor {
    private content: string = "";

    public type(words: string): void {
        this.content += words;
    }

    public getContent(): string { return this.content; }

    public save(): EditorMemento {
        return new EditorMemento(this.content);
    }

    public restore(memento: EditorMemento): void {
        this.content = memento.content;
    }
}

// Опекун
class History {
    private mementos: EditorMemento[] = [];

    public push(memento: EditorMemento): void {
        this.mementos.push(memento);
    }

    public pop(): EditorMemento {
        return this.mementos.pop()!;
    }
}

// Клиентский код
const editor = new TextEditor();
const history = new History();

editor.type("Hello, ");
history.push(editor.save());

editor.type("World!");
console.log(editor.getContent()); // "Hello, World!"

// Отмена последнего действия
const lastState = history.pop();
editor.restore(lastState);
console.log(editor.getContent()); // "Hello, "

Объяснение примера:
TextEditor (Хозяин) может сохранять своё состояние в виде объекта EditorMemento (Снимок). History (Опекун) хранит эти снимки. Когда нам нужно отменить действие, мы достаём последний снимок из истории и передаём его редактору для восстановления состояния. При этом History не имеет доступа к содержимому снимка, что сохраняет инкапсуляцию.

✅ 18. Observer (Наблюдатель)
Определение:
Наблюдатель — это поведенческий паттерн проектирования, который создаёт механизм подписки, позволяющий одним объектам следить и реагировать на события, происходящие в других объектах.

1. Какую проблему решает:
Сильную зависимость между объектами, когда изменение состояния одного должно повлечь за собой изменения в других. Без паттерна издателю пришлось бы знать обо всех своих подписчиках и напрямую вызывать их методы.

2. Условие применения:

Когда изменения в одном объекте могут повлечь за собой изменения в других, и вы не хотите жёстко связывать эти объекты.

Когда точный состав и количество подписчиков заранее неизвестны и могут меняться в рантайме.

3. Каким образом (Решение):
Вводится две роли: Издатель (Subject) и Подписчик (Observer). Издатель имеет методы для подписки, отписки и оповещения подписчиков. Подписчики реализуют общий интерфейс с методом update(). Когда у Издателя происходит важное событие, он перебирает список своих подписчиков и вызывает у каждого метод update().

4. Преимущества и Недостатки:

+ Реализует слабую связанность между издателем и подписчиками.

+ Позволяет отправлять оповещения любому количеству подписчиков.

+ Можно подписывать/отписывать наблюдателей в рантайме.

- Подписчики уведомляются в случайном порядке.

Схема и её пояснение:

[Издатель] <>---- [Подписчик (интерфейс)]
    |                 ^
    |                 | (реализует)
    |                 |
    | (хранит список) |
    v                 v
(уведомляет) --> [Конкретный подписчик А]
               [Конкретный подписчик Б]

Издатель хранит список подписчиков и оповещает их.

Подписчик — интерфейс с методом update().

Конкретные подписчики реализуют этот интерфейс и выполняют действия при получении уведомления.

Пример на TypeScript:

// Интерфейс подписчика
interface IObserver {
    update(data: any): void;
}

// Издатель
class WeatherStation {
    private observers: IObserver[] = [];
    private temperature: number = 0;

    public subscribe(observer: IObserver): void {
        this.observers.push(observer);
    }

    public unsubscribe(observer: IObserver): void {
        this.observers = this.observers.filter(obs => obs !== observer);
    }

    public notify(): void {
        for (const observer of this.observers) {
            observer.update(this.temperature);
        }
    }

    public setTemperature(temp: number): void {
        console.log(`WeatherStation: new temperature is ${temp}`);
        this.temperature = temp;
        this.notify();
    }
}

// Конкретные подписчики
class PhoneDisplay implements IObserver {
    update(temperature: number): void {
        console.log(`PhoneDisplay: It is now ${temperature} degrees.`);
    }
}
class WebsiteDisplay implements IObserver {
    update(temperature: number): void {
        console.log(`WebsiteDisplay: Current temperature updated to ${temperature}.`);
    }
}

// Клиентский код
const weatherStation = new WeatherStation();
const phone = new PhoneDisplay();
const website = new WebsiteDisplay();

weatherStation.subscribe(phone);
weatherStation.subscribe(website);

weatherStation.setTemperature(25);

Объяснение примера:
WeatherStation (Издатель) ничего не знает о PhoneDisplay или WebsiteDisplay. Она просто хранит список объектов, реализующих интерфейс IObserver. Когда температура меняется, станция вызывает метод update у всех подписчиков. Мы можем добавлять или удалять подписчиков, не меняя код метеостанции.

✅ 19. State (Состояние)
Определение:
Состояние — это поведенческий паттерн проектирования, который позволяет объектам менять своё поведение в зависимости от своего внутреннего состояния. Со стороны кажется, что изменился класс объекта.

1. Какую проблему решает:
Наличие в коде больших, громоздких условных операторов (if/else, switch), которые проверяют текущее состояние объекта и в зависимости от него выполняют разную логику. Такой код сложно поддерживать и расширять.

2. Условие применения:

Когда поведение объекта кардинально меняется в зависимости от его внутреннего состояния.

Когда в коде много условных операторов, проверяющих состояние.

Когда логика переходов между состояниями сложна и запутана.

3. Каким образом (Решение):
Вся логика, зависящая от состояния, выносится в отдельные классы-состояния. У всех состояний есть общий интерфейс. Основной объект (Контекст) хранит ссылку на текущий объект-состояние и делегирует ему выполнение работы. При этом и Контекст, и сами объекты-состояния могут инициировать смену состояния, заменяя текущий объект-состояние на новый.

4. Преимущества и Недостатки:

+ Избавляет от множества условных операторов.

+ Концентрирует код для каждого состояния в одном месте.

+ Упрощает добавление новых состояний.

- Усложняет код, если состояний мало и они редко меняются.

Схема и её пояснение:

[Контекст] <>---- [Состояние (интерфейс)]
    |                 ^
    |                 | (реализует)
    | (делегирует)    |
    v                 v
(выполнение) --> [Конкретное состояние А]
                 [Конкретное состояние Б]

Контекст хранит ссылку на текущее состояние и делегирует ему запросы.

Состояние — интерфейс, описывающий методы, зависящие от состояния.

Конкретные состояния реализуют это поведение и могут менять состояние Контекста.

Пример на TypeScript:

class DocumentContext {
    private state: IState;
    constructor() {
        this.state = new DraftState(this);
    }
    public changeState(state: IState): void {
        console.log(`Context: Changing state to ${state.constructor.name}.`);
        this.state = state;
    }
    public publish(): void {
        this.state.publish();
    }
}

interface IState {
    publish(): void;
}

class DraftState implements IState {
    constructor(private context: DocumentContext) {}
    public publish(): void {
        console.log("DraftState: Publishing document...");
        this.context.changeState(new ModerationState(this.context));
    }
}

class ModerationState implements IState {
    constructor(private context: DocumentContext) {}
    public publish(): void {
        console.log("ModerationState: Document approved!");
        this.context.changeState(new PublishedState(this.context));
    }
}

class PublishedState implements IState {
    constructor(private context: DocumentContext) {}
    public publish(): void {
        console.log("PublishedState: Document is already published.");
    }
}

// Клиентский код
const doc = new DocumentContext();
doc.publish(); // Переходит в Moderation
doc.publish(); // Переходит в Published
doc.publish(); // Ничего не делает

Объяснение примера:
Объект DocumentContext может быть в разных состояниях (Draft, Moderation, Published). Вместо проверки if (this.status === 'draft') ... внутри DocumentContext, мы вынесли всю логику в классы DraftState, ModerationState и PublishedState. DocumentContext просто делегирует вызов publish() текущему состоянию.

✅ 20. Strategy (Стратегия)
Определение:
Стратегия — это поведенческий паттерн проектирования, который определяет семейство алгоритмов, помещает каждый из них в собственный класс и делает их объекты взаимозаменяемыми.

1. Какую проблему решает:
Наличие нескольких вариантов одного и того же алгоритма, реализованных через большой условный оператор (if/else или switch). Это делает класс сложным и нарушает принцип единственной ответственности.

2. Условие применения:

Когда у вас есть несколько вариантов одного и того же алгоритма, и нужно переключаться между ними в рантайме.

Когда нужно инкапсулировать и изолировать логику разных алгоритмов от остального кода.

3. Каким образом (Решение):
Различные алгоритмы (Стратегии) реализуются в отдельных классах с общим интерфейсом. Основной класс (Контекст) хранит ссылку на одну из стратегий и делегирует ей выполнение работы, не вдаваясь в детали реализации.

4. Преимущества и Недостатки:

+ Позволяет менять алгоритмы на лету, обеспечивая гибкость.

+ Изолирует код, данные и зависимости алгоритмов от остальной логики.

+ Заменяет наследование композицией, что часто является более гибким подходом.

- Усложняет программу за счёт введения новых классов и интерфейсов.

- Клиент должен знать, в чём разница между стратегиями, чтобы выбрать подходящую.

Схема и её пояснение:

[Контекст] <>---- [Стратегия (интерфейс)]
    |                 ^
    |                 | (реализует)
    | (делегирует)    |
    v                 v
(выполнение) --> [Конкретная стратегия А]
                 [Конкретная стратегия Б]

Контекст хранит ссылку на текущую Стратегию и работает с ней через общий интерфейс.

Стратегия — интерфейс, общий для всех алгоритмов.

Конкретные стратегии реализуют этот интерфейс, каждая по-своему.

Пример на TypeScript:

// Интерфейс Стратегии
interface IRouteStrategy {
    buildRoute(start: string, end: string): void;
}

// Конкретные Стратегии
class RoadStrategy implements IRouteStrategy {
    public buildRoute(start: string, end: string): void {
        console.log(`Building a road route from ${start} to ${end}.`);
    }
}
class WalkingStrategy implements IRouteStrategy {
    public buildRoute(start: string, end: string): void {
        console.log(`Building a walking route from ${start} to ${end}.`);
    }
}

// Контекст
class Navigator {
    private routeStrategy: IRouteStrategy;

    constructor(strategy: IRouteStrategy) {
        this.routeStrategy = strategy;
    }

    public setStrategy(strategy: IRouteStrategy): void {
        this.routeStrategy = strategy;
    }

    public findRoute(start: string, end: string): void {
        this.routeStrategy.buildRoute(start, end);
    }
}

// Клиентский код
const navigator = new Navigator(new RoadStrategy());
console.log("Client: Finding a route for my car.");
navigator.findRoute("Home", "Work");

console.log("\nClient: Now I want to walk.");
navigator.setStrategy(new WalkingStrategy());
navigator.findRoute("Work", "Cafe");

Объяснение примера:
Класс Navigator не знает, как строить маршруты. Он делегирует эту задачу объекту-стратегии. Мы можем легко подменить автомобильную стратегию на пешеходную в рантайме, не меняя код самого Navigator.

✅ 21. Template Method (Шаблонный метод)
Определение:
Шаблонный метод — это поведенческий паттерн проектирования, который определяет скелет алгоритма в суперклассе, но позволяет подклассам переопределять некоторые шаги этого алгоритма, не меняя его структуру в целом.

1. Какую проблему решает:
Дублирование кода в разных классах, которые реализуют похожие алгоритмы с небольшими отличиями.

2. Условие применения:

Когда у разных классов есть очень похожие алгоритмы с небольшими отличиями.

Когда вы хотите позволить подклассам расширять только определённые части алгоритма, оставляя его основную структуру неизменной.

3. Каким образом (Решение):
В базовом абстрактном классе создаётся шаблонный метод, который вызывает последовательность других методов. Некоторые из этих методов реализуются в базовом классе (общие шаги), а некоторые объявляются как абстрактные (шаги, которые должны реализовать подклассы).

4. Преимущества и Недостатки:

+ Устраняет дублирование кода.

+ Позволяет контролировать алгоритм на уровне суперкласса, запрещая подклассам изменять его структуру.

- Может быть сложнее поддерживать из-за жёсткой структуры алгоритма.

- Нарушает Принцип подстановки Лисков, если подкласс переопределяет шаг с нарушением логики базового класса.

Схема и её пояснение:

[Абстрактный класс]
 + templateMethod() {
     - step1() // общий
     - step2() // абстрактный
     - step3() // общий (hook - необязательный)
 }
      ^
      | (наследует)
      |
[Конкретный класс]
 + step2() // реализует
 + step3() // может переопределить

Абстрактный класс определяет templateMethod() и общие шаги.

Конкретный класс реализует только те шаги, которые специфичны для него.

Пример на TypeScript:

abstract class DataMiner {
    // Шаблонный метод
    public mine(): void {
        this.openConnection();
        this.extractData();
        this.parseData();
        this.closeConnection();
    }

    protected openConnection() { console.log("Opening connection..."); }
    protected closeConnection() { console.log("Closing connection..."); }

    protected abstract extractData(): void;
    protected abstract parseData(): void;
}

class PdfDataMiner extends DataMiner {
    protected extractData(): void { console.log("Extracting data from PDF..."); }
    protected parseData(): void { console.log("Parsing PDF data..."); }
}

class CsvDataMiner extends DataMiner {
    protected extractData(): void { console.log("Extracting data from CSV..."); }
    protected parseData(): void { console.log("Parsing CSV data..."); }
}

// Клиентский код
const pdfMiner = new PdfDataMiner();
pdfMiner.mine();

console.log();

const csvMiner = new CsvDataMiner();
csvMiner.mine();

Объяснение примера:
Алгоритм обработки данных (mine) одинаков для всех форматов: открыть, извлечь, разобрать, закрыть. Шаги открытия и закрытия соединения общие для всех и реализованы в базовом классе DataMiner. А шаги извлечения и разбора данных специфичны для каждого формата, поэтому они объявлены как абстрактные и реализуются в подклассах PdfDataMiner и CsvDataMiner.

2. Паттерны GRASP (General Responsibility Assignment Software Patterns)
✅ 1. Information Expert (Информационный эксперт)
Определение:
Информационный эксперт — это фундаментальный принцип GRASP, который гласит, что обязанность следует назначать тому классу, у которого есть вся необходимая для её выполнения информация.

1. Какую проблему решает:
Непонимание, в какой класс поместить ту или иную операцию или бизнес-логику. Это приводит к тому, что логика "размазывается" по разным классам, которые вынуждены постоянно запрашивать данные друг у друга, что увеличивает зацепление (coupling) и снижает связность (cohesion).

2. Условие применения:
Применяется всегда при проектировании классов для решения, какой класс должен быть ответственным за определённое поведение.

3. Каким образом (Решение):
Операция размещается в том классе, который владеет большинством данных, необходимых для её выполнения. Это централизует логику, улучшает инкапсуляцию и делает код более понятным и поддерживаемым.

4. Преимущества и Недостатки:

+ Повышается связность (high cohesion) и инкапсуляция.

+ Снижается зацепление (low coupling), код становится легче поддерживать.

- Слепое следование может привести к появлению "божественных объектов", если один класс накапливает слишком много информации и обязанностей.

Схема и её пояснение:

// Плохо: OrderProcessor запрашивает данные у всех
[OrderProcessor] -- getTotal() --> [Order] -> getPrice() -> [OrderItem]

// Хорошо: Order сам знает, как посчитать свою стоимость
[Клиент] -- getTotal() --> [Order]
                             | (делегирует)
                             v
                          [OrderItem]

Плохой вариант: Внешний класс-сервис (OrderProcessor) вынужден "опрашивать" другие объекты, чтобы собрать данные и выполнить вычисление.

Хороший вариант: Класс Order, который владеет информацией о своих позициях (OrderItem), сам предоставляет метод getTotal(), инкапсулируя логику расчёта.

Пример на TypeScript:

class OrderItem {
    constructor(public price: number, public quantity: number) {}
    // Этот класс - эксперт в расчете своей стоимости
    public getSubtotal(): number {
        return this.price * this.quantity;
    }
}

class Order {
    private items: OrderItem[] = [];

    public addItem(item: OrderItem) { this.items.push(item); }

    // Этот класс - эксперт в расчете общей стоимости заказа
    public getTotal(): number {
        return this.items.reduce((total, item) => total + item.getSubtotal(), 0);
    }
}

// Клиентский код
const order = new Order();
order.addItem(new OrderItem(100, 2));
order.addItem(new OrderItem(50, 3));

// Клиенту не нужно знать, как считается сумма, он просто просит "эксперта"
console.log(`Total order price: ${order.getTotal()}`);

Объяснение примера:
Класс Order обладает всей информацией о позициях заказа (OrderItem). Поэтому именно он является "информационным экспертом" по вычислению общей стоимости и предоставляет метод getTotal(). В свою очередь, OrderItem является экспертом по вычислению своей промежуточной стоимости.

✅ 2. Creator (Создатель)
Определение:
Создатель — это принцип GRASP, который помогает определить, какой класс должен нести ответственность за создание экземпляров других классов.

1. Какую проблему решает:
Беспорядочное создание объектов (new) в разных частях системы. Это приводит к высокой связанности (зацеплению), так как классы, использующие другие объекты, становятся зависимы от их конкретных реализаций, что усложняет замену и тестирование.

2. Условие применения:
Применяется всегда, когда нужно решить, где именно в коде должен находиться оператор new ClassName().

3. Каким образом (Решение):
Ответственность за создание объекта A рекомендуется возложить на класс B, если выполняется одно из условий:

B является агрегатором или контейнером для A (например, Order содержит OrderItem).

B тесно использует A.

B имеет все данные для инициализации A и передаёт их в конструктор.

4. Преимущества и Недостатки:

+ Уменьшает зацепление (low coupling), так как знание о конкретных классах локализуется.

+ Улучшает поддерживаемость, так как логика создания находится в предсказуемом месте.

- Если процесс создания сложный, это может перегрузить класс-создатель. В этом случае лучше применить более специализированные порождающие паттерны (Фабрика, Строитель).

Пример на TypeScript:

class Video {
    constructor(public title: string) {}
}

class Playlist {
    private videos: Video[] = [];
    private title: string;

    constructor(title: string) {
        this.title = title;
    }

    // Playlist является контейнером для Video, поэтому логично,
    // что он отвечает за создание видео в контексте этого плейлиста.
    public addVideo(title: string): void {
        const newVideo = new Video(title); // Creator pattern в действии
        this.videos.push(newVideo);
        console.log(`Video "${title}" added to playlist "${this.title}"`);
    }
}

// Клиентский код
const myPlaylist = new Playlist("Favorites");
myPlaylist.addVideo("Pattern Explained");

Объяснение примера:
Класс Playlist является контейнером для объектов Video. Согласно принципу Creator, именно Playlist является лучшим кандидатом на роль создателя объектов Video. Он инкапсулирует логику создания и добавления видео, и клиенту не нужно делать это самому.

✅ 3. Controller (Контроллер)
Определение:
Контроллер — это принцип GRASP, который назначает ответственность за обработку системных событий и внешних запросов специальному объекту-контроллеру, который выступает в роли посредника между "внешним миром" (UI, API) и доменной моделью.

1. Какую проблему решает:
Смешивание бизнес-логики с кодом пользовательского интерфейса или обработчиками API-запросов (например, вся логика находится в обработчике нажатия кнопки). Это приводит к "раздуванию" UI-классов, низкой переиспользуемости и сложности тестирования бизнес-логики.

2. Условие применения:

При обработке входящих запросов от пользователя или внешней системы.

В архитектурах, где требуется чёткое разделение между представлением (View) и моделью (Model), например, в MVC, MVP, MVVM.

3. Каким образом (Решение):
Создаётся класс-Контроллер, который принимает запрос. Он не выполняет бизнес-логику сам, а находит нужные объекты доменной модели и делегирует им выполнение работы. Он координирует действия, но не содержит бизнес-правил.

4. Преимущества и Недостатки:

+ Разделяет ответственность (Separation of Concerns), отделяя UI от бизнес-логики.

+ Повышает переиспользуемость бизнес-логики (её можно использовать с разными UI).

+ Упрощает тестирование доменных объектов.

- Контроллер может стать слишком раздутым (Bloated Controller), если на него возложить слишком много несвязанных обязанностей.

Пример на TypeScript:

// Модель
class User {
    constructor(public name: string) {}
    save() { console.log(`Saving user ${this.name} to database...`); }
}

// Контроллер
class UserController {
    public createUser(userName: string): void {
        if (!userName) {
            console.error("Username cannot be empty");
            return;
        }
        // 1. Контроллер принимает данные
        // 2. Делегирует создание и сохранение доменной модели
        const user = new User(userName);
        user.save();
    }
}

// Представление (View) - симуляция
class UserForm {
    private controller = new UserController();

    public onSubmit(nameFromInput: string): void {
        // UI не содержит логики, он просто вызывает контроллер
        this.controller.createUser(nameFromInput);
    }
}

// Клиентский код
const form = new UserForm();
form.onSubmit("John Doe");

Объяснение примера:
Класс UserForm (представление) не пытается сам создать и сохранить пользователя. Он просто передает введённые данные в UserController. Контроллер валидирует данные и делегирует основную работу доменному объекту User. Таким образом, логика отделена от UI.

✅ 4. Low Coupling (Низкое зацепление / Слабая связанность)
Определение:
Низкое зацепление — это принцип, требующий минимизировать зависимости между классами. Классы должны знать как можно меньше о внутреннем устройстве друг друга.

1. Какую проблему решает:
Проблему "хрупкости" системы. Когда классы сильно связаны друг с другом (сильное зацепление), изменение в одном классе вызывает каскадные изменения во многих других. Это усложняет поддержку, рефакторинг и тестирование.

2. Условие применения:
Применяется всегда при проектировании любых взаимодействий между компонентами системы. Это одна из ключевых целей хорошего дизайна.

3. Каким образом (Решение):
Уменьшать прямые связи между классами. Использовать интерфейсы для определения контрактов, а не конкретные классы. Применять паттерны, снижающие связанность, такие как Посредник, Наблюдатель, Фасад.

4. Преимущества и Недостатки:

+ Улучшает поддерживаемость: изменения в одном компоненте меньше влияют на другие.

+ Повышает переиспользуемость: независимые компоненты легче использовать в других контекстах.

+ Упрощает понимание системы, так как можно анализировать компоненты в изоляции.

- Чрезмерное следование может привести к созданию большого количества промежуточных классов и интерфейсов, что иногда усложняет навигацию по коду.

Пример на TypeScript:

// Сильное зацепление (ПЛОХО)
class BadReportGenerator {
    // Зависит от КОНКРЕТНОГО класса PdfExporter
    private exporter = new PdfExporter();

    generate() {
        console.log("Generating report...");
        this.exporter.exportToPdf();
    }
}
class PdfExporter { exportToPdf() { console.log("Exporting to PDF..."); } }

// Слабое зацепление (ХОРОШО)
interface IReportExporter { export(): void; } // Зависимость от абстракции

class CsvExporter implements IReportExporter { export() { console.log("Exporting to CSV..."); } }

class GoodReportGenerator {
    // Зависит от ИНТЕРФЕЙСА, а не от конкретного класса
    constructor(private exporter: IReportExporter) {}

    generate() {
        console.log("Generating report...");
        this.exporter.export();
    }
}

// Клиентский код
const csvExporter = new CsvExporter();
const goodGenerator = new GoodReportGenerator(csvExporter);
goodGenerator.generate();

Объяснение примера:
BadReportGenerator жёстко связан с PdfExporter. Если мы захотим экспортировать в CSV, нам придётся изменять код BadReportGenerator. GoodReportGenerator зависит не от конкретного класса, а от интерфейса IReportExporter. Мы можем передать ему любой экспортер (CSV, PDF, JSON), который реализует этот интерфейс, не меняя сам генератор отчётов.

✅ 5. High Cohesion (Высокая связность)
Определение:
Высокая связность — это принцип, требующий, чтобы обязанности одного класса были тесно связаны и сфокусированы на одной чётко определённой задаче.

1. Какую проблему решает:
Проблему появления "божественных объектов" (God Objects) — классов, которые делают всё и сразу. Такие классы сложно понимать, поддерживать, тестировать и переиспользовать.

2. Условие применения:
Применяется всегда при определении набора методов и полей для одного класса. Это вторая ключевая цель хорошего дизайна после Low Coupling.

3. Каким образом (Решение):
Не помещать в один класс несвязанные между собой обязанности. Если класс начинает делать слишком много, его следует разделить на несколько более мелких и сфокусированных классов.

4. Преимущества и Недостатки:

+ Классы становятся проще для понимания и поддержки.

+ Повышается надёжность, так как логика не "размазана".

+ Улучшается переиспользуемость сфокусированных классов.

- Чрезмерное дробление может привести к созданию большого количества мелких классов, что иногда усложняет общую картину.

Пример на TypeScript:

// Низкая связность (ПЛОХО)
class BadManager {
    // Этот класс делает всё: и работает с данными, и отображает их
    getUsersFromDB() { /* ... */ }
    getProductsFromDB() { /* ... */ }
    displayUsersAsHtml() { /* ... */ }
    displayProductsAsJson() { /* ... */ }
}

// Высокая связность (ХОРОШО)
class UserRepository { // Отвечает только за данные пользователей
    getUsers() { /* ... */ }
}
class ProductRepository { // Отвечает только за данные продуктов
    getProducts() { /* ... */ }
}
class HtmlView { // Отвечает только за отображение в HTML
    render(data: any) { /* ... */ }
}

// Клиентский код
const userRepo = new UserRepository();
const view = new HtmlView();
// const users = userRepo.getUsers();
// view.render(users);

Объяснение примера:
Класс BadManager нарушает принцип высокой связности, так как он занимается и доступом к данным, и их представлением. Правильный подход — разделить эти обязанности на несколько классов: UserRepository отвечает только за пользователей, ProductRepository — за продукты, а HtmlView — за отображение. Каждый класс имеет одну чёткую и понятную зону ответственности.

3. Принципы проектирования
DRY (Don’t Repeat Yourself / Не повторяйся)

Определение: Каждая часть знания в системе должна иметь единственное, однозначное и авторитетное представление. Проще говоря, избегайте дублирования кода.

Пример: Вместо того чтобы иметь одинаковый код для валидации email в трёх разных местах, создайте одну функцию isValidEmail(email) и вызывайте её.

// ПЛОХО: Дублирование логики
if (!email.includes('@')) { /* ошибка */ }
// ...в другом месте...
if (!email.includes('@')) { /* другая ошибка */ }

// ХОРОШО: Одна функция
function isValidEmail(email: string): boolean {
    return email.includes('@');
}
if (!isValidEmail(email)) { /* ... */ }

KISS (Keep It Simple, Stupid / Делай проще, дурачок)

Определение: Системы работают лучше всего, если они остаются простыми, а не усложняются без необходимости. Всегда выбирайте самое простое решение, которое работает.

Пример: Если вам нужно получить название дня недели по его номеру, простой массив или switch гораздо лучше, чем сложный класс DayOfWeekFactory.

// СЛОЖНО (Over-engineering)
class DayFactory { create(dayNum: number) { /* ... */ } }

// ПРОСТО (KISS)
const days = ["Monday", "Tuesday", ...];
const dayName = days[dayNumber - 1];

YAGNI (You Aren’t Gonna Need It / Вам это не понадобится)

Определение: Не добавляйте функциональность впрок, до того как она действительно понадобится. Реализуйте только то, что требуется прямо сейчас.

Пример: Команда решает добавить в класс User поле faxNumber и логику его валидации, "на всякий случай, вдруг понадобится в будущем", хотя в текущих требованиях этого нет. Это лишняя работа и усложнение кода.

SOLID:

S - Single Responsibility Principle (Принцип единственной ответственности): Класс должен иметь только одну причину для изменения.

Пример: Класс Report не должен сам себя сохранять в файл. Его ответственность — содержать данные отчёта. Сохранением должен заниматься другой класс, например, ReportPersistence.

O - Open/Closed Principle (Принцип открытости/закрытости): Сущности должны быть открыты для расширения, но закрыты для модификации.

Пример: Чтобы добавить новый способ экспорта отчёта (например, в CSV), не нужно изменять существующий класс ReportGenerator. Вместо этого можно добавить новый класс CsvExporter, реализующий общий интерфейс IExporter, и передать его в ReportGenerator.

L - Liskov Substitution Principle (Принцип подстановки Барбары Лисков): Объекты в программе должны быть заменяемы на экземпляры их подтипов без изменения правильности выполнения программы.

Пример: Классическая проблема "Квадрат-Прямоугольник". Если Square наследуется от Rectangle, то он нарушает этот принцип. Метод, который работает с Rectangle и меняет его ширину, не ожидает, что при этом изменится и высота, как это произойдёт у Square.

I - Interface Segregation Principle (Принцип разделения интерфейса): Клиенты не должны быть вынуждены зависеть от методов, которые они не используют.

Пример: Вместо одного "толстого" интерфейса IWorker { work(); eat(); } лучше создать два маленьких: IWorkable { work(); } и IFeedable { eat(); }. Тогда класс Robot сможет реализовать только IWorkable.

D - Dependency Inversion Principle (Принцип инверсии зависимостей): Модули верхних уровней не должны зависеть от модулей нижних уровней. Оба должны зависеть от абстракций.

Пример: Сервис PaymentProcessor не должен напрямую зависеть от конкретного класса StripeGateway. Он должен зависеть от интерфейса IPaymentGateway, а StripeGateway будет его реализацией. Это позволяет легко подменить Stripe на PayPal, не меняя PaymentProcessor.

4. Анти-паттерны
Big ball of mud (Большой ком грязи)

Что это: Система без чётко выраженной архитектуры, где всё связано со всем. Часто это один или несколько огромных файлов, где смешаны бизнес-логика, работа с БД, UI и т.д.

Пример: Файл main.js на 5000 строк, в котором находятся обработчики API-запросов, логика валидации форм, прямые SQL-запросы и манипуляции с DOM.

Software Bloat (Раздувание ПО)

Что это: Программа, которая со временем становится чрезмерно большой и медленной из-за добавления множества ненужных функций или неэффективной реализации.

Пример: Простой текстовый редактор, который для открытия пустого файла использует 500 МБ оперативной памяти, потому что в него "на всякий случай" встроили почтовый клиент и систему управления проектами.

Yo-yo problem (Проблема йо-йо)

Что это: Ситуация, когда из-за слишком глубокой и сложной иерархии наследования или запутанных вызовов разработчику приходится постоянно "прыгать" между множеством файлов, чтобы понять, какой именно код выполняется.

Пример: Чтобы понять, что делает метод obj.doSomething(), нужно посмотреть 5 родительских классов и 3 интерфейса, чтобы найти его реализацию.

Magic Button (Волшебная кнопка)

Что это: Элемент интерфейса (кнопка), обработчик onClick которого содержит сотни строк несвязанной бизнес-логики вместо того, чтобы делегировать её другим объектам.

Пример: saveButton.onClick = () => { /* 200 строк кода: валидация, сохранение в БД, отправка email, логирование, обновление UI... */ }

Magic Number (Магическое число)

Что это: Использование в коде неименованных числовых или строковых констант, смысл которых непонятен без глубокого анализа контекста.

Пример: if (user.status === 2) — что значит 2? Непонятно. Правильно: const ORDER_STATUS_SHIPPED = 2; if (user.status === ORDER_STATUS_SHIPPED).

Gas Factory (Газовая фабрика)

Что это: Синоним избыточного усложнения (over-engineering). Создание слишком сложных, "навороченных" и ненужных абстракций для решения простой задачи.

Пример: Для создания простого объекта User с двумя полями разработчик реализует паттерны Abstract Factory, Builder и Prototype одновременно, хотя достаточно простого конструктора.

Interface Bloat (Раздувание интерфейса)

Что это: Создание "толстого" интерфейса с множеством методов, которые не все классы-реализаторы могут или должны поддерживать. Нарушает принцип разделения интерфейса (ISP).

Пример: Интерфейс IFile { read(); write(); delete(); changePermissions(); }. Класс ReadOnlyFile может реализовать только read(), а остальные методы ему придётся "заглушить", выбрасывая исключение.
